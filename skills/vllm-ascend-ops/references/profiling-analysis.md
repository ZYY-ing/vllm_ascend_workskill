# Profiling分析：从trace到可验证结论

只在用户需要解释性能或对比优化时读取；普通部署不自动生成一套分析框架。先按[采集流程](profiling.md)确认本轮数据完整及各rank解析成功。

## 1. 确认数据可比较

读取本轮provenance与实际服务参数：模型层数、注意力类型、MoE结构、量化、MTP方法/步数、图模式、TP/DP/EP、设备和通信后端。结构数字来自当前模型配置及执行证据，不沿用其他模型示例。

对比两次实验时明确改变的变量，并列出其余差异：代码/补丁、镜像/依赖、输入输出、并发、缓存命中、稳态阶段、图捕获、rank、profiler配置和采集时长。不能把不同代码或不同负载下通信耗时的变化直接归因为拓扑。存在混杂时报告“观察到差异，尚不能归因”，建议只改变一个变量的最小复测。

先核对文件时间、单位、rank和字段含义。工具可能在不同版本改变Duration、Wait Time或聚合桶定义；缺少某计数器不等于该项为零。

## 2. 选择对应阶段与统计单位

- 将冷启动、编译/图捕获、预热、长prefill、稳定decode和尾部请求分开；用户要端到端时另报完整范围，不能只截最快片段。
- 对decode可按iteration/forward分析周期及分布；同时报告有效forward数、p50与尾部。p50较少受偶发长尾影响，但仍会受阶段混杂影响，不能只报p50隐藏异常。
- MTP每轮验证/接收的token数可能变化，不能只以forward变快就断定用户输出吞吐更高；同时核对接收率、真实输出tokens、TPOT及服务吞吐。
- 比较具体rank及最慢rank；多机时钟不同或异步活动重叠时，不能直接相加各rank耗时作为端到端周期。

## 3. 看时间线，而不只看汇总占比

step_trace_time、op_statistic等用于筛选重点，不单靠Free桶或某类百分比断定空闲。使用trace/kernel时间区间核对相应周期内计算、通信及全流静默：

1. 确认同一时间域、同一rank和同一有效窗口。
2. 对关注活动的[start,end]区间求并集，再除以窗口长度，避免多个stream重叠重复计费。
3. 按当前采集能力区分计算kernel、通信、拷贝及host侧空隙；没有记录到的活动不等于没有发生。

union busy率是所选活动的观察值，不直接等于NPU利用率，更不能单凭低值判断CPU瓶颈。需要结合host launch、同步点、队列、请求进展和其他rank。

## 4. 从热点定位到机制

| 观察 | 下一步验证 |
|---|---|
| GEMM/attention耗时突出 | 核对input shapes、dtype、batch、序列长度、实现及是否含等待；不能只看算子名称 |
| dispatch/combine或集合通信突出 | 查当前代码实际调用路径、通信组、参与rank、payload与非重叠时间，区分TP、EP、序列并行等机制 |
| 计算利用指标低 | 核对工具定义、是否采到硬件计数、访存等待/带宽、shape和占用；低值不是“带宽瓶颈”的充分证据 |
| 大段allGather或等待 | 沿时间线找最早慢rank和上游触发点；等待算子可能是失步症状，不一定是最初原因 |
| Graph与eager行为不同 | 保持其他条件一致做诊断对照；改善只说明需深入图路径，也可能混入内存/调度变化，不能立刻断定某个capture bug |

aiv_vec_ratio、aiv_mte2_ratio、cube_utilization等字段只在该设备/工具确实提供并核对含义后使用。不要把其他模型观察到的固定百分比当通用判据。检查Duration是否含等待，避免再把Wait Time重复加一遍；同名通信也不必然来自同一并行机制。

## 5. 报告与下一步

给出简洁对照表：实验标识、有效周期数、周期p50/尾部、主要计算、通信/等待证据、真实输出吞吐与TTFT/TPOT。对存在重叠的类别，不将耗时简单求和成“总时间”。

每个结论指向文件/rank/时间窗/算子或调用路径，注明口径、混杂和置信程度，再提出最小复测项。将“热点是什么”“为什么慢”“修改后是否有效”分开；未做对照不能宣布某优化收益，也不能只凭热点排名就修改模型代码。

方法参考：[Blue Toolkit profiling分析](https://github.com/xuchi-0808/blue-server-toolkit/blob/main/docs/vllm-profiling-analysis.md)。本技能保留其结构锚定和逐算子核查思路，具体数字、字段语义及因果结论均需在本轮验证。
